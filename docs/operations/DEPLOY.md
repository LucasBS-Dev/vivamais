# Implantação econômica

Configurações preparadas; nenhum serviço externo foi criado ou publicado. Manter a demo com contas sintéticas e revisão humana antes de contratação/publicação.

1. Criar repositório **privado** e conectar contas pessoais/institucionais apropriadas. Revisar CUSTOS.md e limites nos painéis.
2. Supabase Free: criar PostgreSQL, guardar conexão somente nos secrets Railway, escolher conexão direta IPv6 se suportada ou pooler de sessão IPv4 (porta 5432) compatível com JDBC/Flyway. Não usar pooler transacional para migração sem validação específica. Exigir TLS (`sslmode=verify-full`, com cadeia confiável); URL no formato `jdbc:postgresql://host:5432/postgres?...`. Não usar as tabelas clínicas pelo SDK de cliente Supabase. Revogar acesso anônimo/autenticado do PostgREST ao schema da API antes de inserir dados de demonstração. Usar usuário de runtime com privilégios mínimos e credencial separada de migração antes de dados reais; o proprietário de migração não garante isolamento contra comprometimento da aplicação.
3. Railway Hobby: definir **Root Directory `/backend/demo`** e Config File `/infra/railway.toml` (caminho a partir da raiz do repositório). Assim o contexto contém pom.xml/src e `dockerfilePath="Dockerfile"` aponta para backend/demo/Dockerfile. Secrets DATABASE_URL, DATABASE_USER, DATABASE_PASSWORD, CORS_ALLOWED_ORIGINS. PORT é fornecido pela plataforma. 1 réplica, alvo inicial até 1 GB, pool 4, heap 60% e headroom para memória nativa. Health `/actuator/health`. Profile bootstrap apenas na provisão explícita; retirar senha e profile depois. Evitar duplicar instâncias porque o limitador de login desta fundação é por processo; adicionar limite central no gateway antes de escalar. Configuração não foi validada em conta Railway nesta etapa.
4. Vercel Hobby: root directory web, framework Next.js, instalação na raiz do monorepo com `pnpm install --frozen-lockfile`; comando build `pnpm --filter @viva/web build`. API_BASE_URL aponta para HTTPS público Railway; APP_ORIGIN para HTTPS web exato. Esses valores são server-side. Confirmar cookie Secure, origem, headers sem cache e recursos indisponíveis quando a API falha. Hobby requer elegibilidade de uso pessoal não comercial.
5. App: configurar EXPO_PUBLIC_API_BASE_URL com **a mesma API HTTPS**, identificadores definitivos de pacote/bundle e vínculo EAS no ambiente seguro. Não inserir secrets backend no app. Seguir publicação e testes físicos de LOJAS.md. Não depender de Expo Go nem túnel para revisão final.
6. Storage já possui implementação: escolher STORAGE_BACKEND=supabase no servidor, configurar SUPABASE_URL, SUPABASE_STORAGE_BUCKET privado e SUPABASE_SERVICE_ROLE_KEY exclusivamente no Railway. Definir FILES_ENCRYPTION_KEY estável (32 bytes em base64, gerada e guardada em ambiente seguro) antes do primeiro upload; preservar essa chave separada do backup. O backend valida/sanitiza PNG/JPEG, remove metadados e cifra os objetos antes de armazenar. Links são curtos, autorizados e vinculados à sessão. Testar o adaptador no fornecedor antes de publicar: a validação atual cobre o armazenamento local real. Tesseract está no Dockerfile; testar OCR com imagem sintética e revisão obrigatória. Serviço alimentar depende de endpoint/chave/critérios e referência de aprovação; não habilitar análise fictícia.

Antes de demonstração e revisão das lojas: abrir painel Supabase e verificar se projeto foi pausado; restaurar oficialmente, aguardar disponibilidade, testar health, login, identidade e isolamento ponta a ponta. Sem tráfego artificial para contornar pausa. Se incompatível com disponibilidade exigida, avaliar Neon PostgreSQL e R2 privado após aprovação; migrações e API permanecem iguais.
